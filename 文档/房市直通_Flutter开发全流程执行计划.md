## 1. 项目概述

### 1.1 项目背景

传统房产平台通常将房源展示与中介咨询、房屋评估、线下带看、交易撮合等服务结合。部分只希望发布或查询房源的用户，可能并不需要这些复杂服务。

"房市直通"计划提供一个独立、简洁的房产信息发布与查询渠道，让房屋出售方、购房者和第三方专业服务人员能够通过平台获取信息并自主建立联系。

### 1.2 项目目标

第一版需要形成以下可运行闭环：

``` text
用户注册/登录
      ↓
发布者填写房源并上传图片
      ↓
平台进行必要的信息审核
      ↓
审核通过后公开展示
      ↓
购房者浏览、搜索和筛选房源
      ↓
购房者发起固定问题
      ↓
发布者选择预设回复
      ↓
双方分别确认是否交换联系方式
      ↓
双方自行在线下继续沟通
```

第三方房产服务机构拥有独立的信息展示与入驻审核流程，不参与上述房源主流程。

### 1.3 项目成功标准

-   用户能够完成注册、登录和个人资料管理。
-   发布者能够免费发布、编辑、暂停、续期和下架房源。
-   购房者能够免费浏览、搜索、筛选和收藏房源。
-   双方能够完成固定选项式意向交流。
-   联系方式只有在双方分别授权后才可展示。
-   第三方机构能够提交入驻申请，管理员能够审核并管理其公开资料。
-   管理员能够审核房源、处理举报和管理用户。
-   Android 测试包能够安装运行，核心流程无阻断性缺陷。
-   后端具备日志、备份、权限校验和基础异常监控能力。

## 2. 产品范围与原则

### 2.1 产品定位

**不做房屋交易的中间商，只做免费、透明、直接的房产信息连接者。**

平台主要提供：

1.  房源信息发布。
2.  房源信息展示与检索。
3.  房源状态管理。
4.  固定问题与预设回复。
5.  双方自愿交换联系方式。
6.  第三方房产服务信息展示。
7.  房源、机构和举报信息的后台管理。

### 2.2 免费原则

V1.0 阶段不设置以下收费项目：

-   不收取房源发布费。
-   不收取房源查看费。
-   不收取第三方入驻费。
-   不收取房屋成交佣金。
-   不设置会员、付费解锁或付费排名。

因此第一版不需要开发支付、退款、订单收费、余额或结算模块。

### 2.3 明确不做的功能

第一版不开发：

-   房屋专业估价或自动估价。
-   线下带看或预约看房。
-   房屋交易撮合、议价代理或交易担保。
-   在线签约、贷款办理和房款支付。
-   资金托管、定金收付或过户办理。
-   视频上传、视频通话和直播。
-   自由文本即时聊天。
-   复杂智能推荐、房价预测和地图找房。
-   第三方服务在线下单、支付或派单。

平台不介入房屋买卖双方及第三方机构之间的线下合同和资金往来，但仍须履行适用法律法规要求的信息管理、个人信息保护和消费者权益保障义务。

### 2.4 首发范围

建议首期选择一个城市的一个或少数几个区域，以个人二手住宅信息为主。

首期不同时覆盖新房、租房、商铺、厂房、土地等复杂类别，以降低表单、审核规则和运营难度。

## 3. 用户角色与权限

  -------------------------------------------------------------------------------------------------
  角色                    主要能力                                   限制
  ----------------------- ------------------------------------------ ------------------------------
  游客                    浏览公开房源、搜索、查看公开机构信息       不能发布、收藏或发起意向

  注册用户                发布房源、收藏、发起意向、管理自己的房源   不能操作他人房源

  房源发布者              管理自己发布的房源、回复意向               只能管理本人有权发布的房源

  第三方服务人员          申请机构身份、维护获批的服务资料           审核通过前不能公开展示

  管理员                  审核房源和机构、处理举报、管理账户         操作必须留痕，按权限访问数据
  -------------------------------------------------------------------------------------------------

一个普通用户可以同时是购房者和房源发布者，不要求分别注册账号。第三方服务身份作为用户账户上的附加身份，经审核后启用。

### 3.1 权限设计原则

-   所有权限由后端验证，不能仅靠 Flutter 隐藏按钮。
-   用户只能修改自己拥有的房源。
-   普通用户不能修改审核状态。
-   联系方式接口必须校验双方授权。
-   管理员按职责分配权限，重要操作记录审计日志。
-   管理员不能无理由浏览与工作无关的敏感个人信息。

## 5. 核心业务流程

### 5.1 房源发布流程

``` text
登录
  ↓
进入“发布”
  ↓
填写基础信息
  ↓
上传房屋照片
  ↓
确认发布权限及信息声明
  ↓
保存草稿或提交审核
  ↓
管理员审核
  ├── 通过 → 房源公开展示
  └── 驳回 → 展示原因，允许修改后重提
```

房源表单建议包括：

  字段              要求
  ----------------- --------------------
  城市              必填
  区域              必填
  小区名称          必填
  建筑面积          必填，明确单位
  户型              必填
  所在楼层/总楼层   可选
  出售总价          必填，统一使用万元
  装修情况          可选
  房屋朝向          可选
  房屋描述          可选，限制字数
  房屋图片          建议 1---6 张
  发布者身份        房主、授权代理人等
  发布权限声明      必须确认

发布者必须确认其有权发布相关信息。平台不应把账户身份核验表述为房屋产权核验。

### 5.2 房源状态

建议统一使用以下状态：

  状态               含义
  ------------------ --------------------------
  `draft`            草稿
  `pending_review`   待审核
  `published`        展示中
  `paused`           发布者主动暂停
  `sold`             发布者标记已售
  `expired`          展示有效期结束
  `rejected`         审核驳回
  `removed`          管理员下架或用户删除展示

建议采用以下有效期策略：

-   房源公开展示期限为 30 天。
-   在第 7、14、27
    天向发布者发送状态确认提醒（提醒渠道可在后续版本实现）。
-   发布者可以随时主动暂停或标记已售。
-   到期后自动转为 `expired`，停止公开展示和新的意向交流。
-   发布者可以免费确认信息并续期。
-   修改价格、位置、发布主体等关键字段时，根据审核规则重新审核。

### 5.3 浏览与筛选流程

``` text
首页
  ↓
输入小区/区域关键词
  ↓
选择区域、总价、面积、户型
  ↓
查看符合条件的房源列表
  ↓
打开房源详情
  ↓
收藏或发起意向交流
```

免费公开信息建议包括：区域、小区名称（经审核后）、总价、面积、户型、部分房屋描述、房源状态和最近确认日期。

房主手机号、身份证件、精确门牌号等敏感信息不得默认公开。

### 5.4 固定回复流程

采用三阶段预设问答，不开发自由文本聊天。

**第一阶段：确认房源状态**

问题：房屋目前是否仍在出售？

回复选项：

-   仍在出售。
-   暂停出售。
-   已经售出。

若发布者选择暂停或已售出，应结束当前意向，并更新房源状态或提示发布者同步更新房源。

**第二阶段：确认议价意愿**

问题：房屋价格是否可以协商？

回复选项：

-   可以协商。
-   暂不议价。

**第三阶段：确认联系意愿**

问题：是否愿意进一步交换联系方式？

回复选项：

-   愿意。
-   暂不愿意。

双方都表达愿意后，进入独立的联系方式授权页面。

### 5.5 联系方式授权

-   买方和发布者分别确认是否公开自己的联系方式。
-   双方都授权后，后端才允许查看本次交流所需的联系信息。
-   用户可以选择公开手机号或其他主动填写的联系方式。
-   未授权时，API 不得返回联系方式字段。
-   用户撤回授权后，平台停止后续展示。
-   页面提示：对方已经查看或保存的信息无法由平台远程收回。

不能仅通过前端按钮控制授权，必须在服务端实施校验并记录授权时间、授权对象和授权范围。

### 5.6 第三方服务流程

``` text
第三方用户注册
  ↓
提交机构/个人服务资料
  ↓
上传必要的资质材料
  ↓
管理员审核
  ├── 通过 → 公开展示服务信息
  └── 驳回 → 修改后重新申请
  ↓
普通用户浏览机构资料
  ↓
用户自主联系第三方
```

服务类别：

-   房地产估价。
-   产权信息咨询。
-   交易材料咨询。
-   不动产过户代办。
-   其他依法可提供的房产专业服务。

依法需要资质或执业资格的业务，只能由符合条件的主体开展。平台应核验与展示相匹配的资质信息，不得把普通入驻等同于专业认证。

## 7. 视觉设计规范

### 7.1 交互原则

-   主要操作有明确按钮。
-   普通操作不频繁弹出确认框。
-   删除、下架、注销、联系方式授权等重要操作需要确认。
-   页面必须包含加载、空数据、失败和重试状态。
-   表单错误提示放在对应字段附近。
-   提交过程中禁用重复提交。
-   页面返回时保留未提交表单内容或提示保存草稿。

### 7.2 房源卡片

房源列表卡片至少展示：

-   房屋封面照片。
-   小区名称。
-   区域。
-   户型。
-   建筑面积。
-   出售总价。
-   当前状态。
-   最近确认在售日期。

图片比例、价格格式和信息顺序在全 APP 保持一致。

### 7.3 无障碍与适配

-   触控目标尽量不小于 44---48 dp。
-   不只用颜色表达状态，配合文字标签。
-   重要文字与背景保持足够对比度。
-   支持系统字体缩放。
-   避免固定高度造成文本裁切。
-   适配常见 Android 手机尺寸，后续验证 iOS 和平板。

### 8.2 技术栈

  层次           技术                                   用途
  -------------- -------------------------------------- ----------------------
  移动端         Flutter + Dart                         Android、后续 iOS
  状态管理       Riverpod                               用户和业务状态

## 12. 安全、隐私与合规要求

本项目涉及房源、手机号、身份材料和第三方机构资质资料，必须在开发阶段落实保护措施。

### 12.1 账户与身份

-   手机验证码登录需限流和防刷。
-   Token 安全存储，不写入普通日志。
-   管理员启用更严格的登录保护。
-   身份核验只收集实现业务所必需的信息。
-   账户注销应有明确流程和数据处理说明。

### 12.2 联系方式保护

-   房主手机号不出现在公开房源详情 API。
-   双方分别授权后才允许读取本次交流所需联系方式。
-   授权行为在服务端记录。
-   撤回授权后停止后续展示。
-   对联系方式读取进行访问日志记录。
-   页面明确提示信息一旦被对方查看或保存，平台无法远程收回。

### 12.3 图片安全

-   限制图片数量、格式和大小。
-   服务端校验真实文件类型，不能只信任扩展名。
-   上传前压缩并移除不必要的 EXIF 定位信息。
-   图片访问采用合理的公开或授权策略。
-   不允许上传身份证件、私人联系方式等不必要的敏感材料。
-   第三方资质文件不应使用公开永久链接。

### 12.4 内容管理

-   房源发布需确认合法发布权限。
-   提供举报入口。
-   管理员审核、驳回和下架操作留痕。
-   对明显违法、侵权、虚假或违规信息按适用规则处理。
-   明确区分"账户身份核验"和"房屋产权核验"。

### 12.5 中国大陆运营前检查

若在中国大陆公开提供服务，应根据实际运营主体、业务模式和部署方式，确认：

-   APP 备案及相关互联网信息服务手续。
-   经营性互联网信息服务是否涉及许可要求。
-   房地产网络信息发布的适用监管要求。
-   个人信息保护、数据安全和网络安全义务。
-   用户协议、隐私政策、举报投诉和注销机制。
-   第三方估价及过户代办业务的主体和资质要求。

本方案不是法律意见，也不代表已经取得任何许可或备案。正式上线前应向主管部门或专业法律顾问核实。

## 18. 风险清单与应对措施

  ----------------------------------------------------------------------------------
  风险                    影响                    应对措施
  ----------------------- ----------------------- ----------------------------------
  初期房源数量少          用户缺乏使用动力        从单一区域开始积累房源

  虚假或过期房源          损害平台可信度          身份核验、状态确认、举报和下架

  免费发布导致垃圾信息    审核负担增加            频率限制、重复内容检测、人工审核

  联系方式泄露            个人信息风险            双方授权、服务端校验、访问日志

  第三方资质不实          用户误信服务宣传        核验材料、明确服务主体和展示范围

  图片存储成本增加        运维成本上升            图片压缩、数量和大小限制

### 18.1 试点验证建议

-   有效房源数量。

-   房源过期和下架比例。
-   房源详情访问量。
-   意向发起数量。
-   双方完成联系授权的比例。
-   虚假信息和举报数量。
-   用户反馈与实际使用障碍。

不要只以注册用户数量作为项目成功指标，应重点关注真实有效房源和双方实际联系情况。

## 最终执行原则

本项目的开发顺序应始终围绕一条主线：

**先完成房源发布与浏览，再完成固定交流和联系方式授权，最后补充第三方服务和后台管理。**

第一版不追求功能数量，不开发与核心定位无关的复杂系统。所有功能以"是否帮助用户更方便地发布、查找和联系房源"为判断标准。

技术上采用 Flutter + Dart 构建移动端，NestJS + PostgreSQL
提供业务服务，Flutter Web
构建管理后台。通过模块化工程、统一组件和清晰的接口边界，保证项目可以先小规模运行，再逐步扩展。

**V1.0
的最终交付目标：一个能够真实发布和查询房源、完成固定意向交流、保护双方联系方式，并支持管理员审核与维护的免费房产信息直连平台。**
