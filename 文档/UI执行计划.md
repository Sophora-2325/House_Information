# 房市直通 APP UI布局设计方案

**项目名称：房市直通**

**开发框架：Flutter + Dart**

**设计平台：Android优先，兼容iOS，独立适配Flutter Web管理后台**

**UI设计版本：V1.0**

---

## 一、整体UI设计理念

### 1.1 设计定位

房市直通定位为轻量化房产信息共享平台，主要服务于房屋出售方、购房者及第三方房产专业服务人员。

界面应突出房源信息的真实性、可读性和获取效率，不采用传统房产平台中过多的广告位、营销弹窗、服务推荐和复杂入口。

主要遵循以下原则：

1. **信息优先：** 首页重点展示房屋图片、价格、面积、户型及位置，让用户快速判断房源是否符合需求。
2. **操作简单：** 发布、查看、联系等核心功能应有清晰入口，尽量减少不必要的跳转。
3. **视觉统一：** 全局统一颜色、字体、按钮、卡片、图标和间距规范。
4. **适合不同年龄用户：** 文字保持清晰，按钮具有足够大的点击区域，避免过度依赖隐藏手势。
5. **尊重隐私：** 个人联系方式默认隐藏，双方授权后才能展示。
6. **功能克制：** 不加入广告轮播、交易支付、在线带看、智能估价和复杂聊天等非核心界面。

### 1.2 设计风格

采用现代简约风格，参考Material Design 3的基本设计原则。

整体以白色背景、蓝绿色强调色和浅灰色分区为主，减少高饱和度颜色的使用。

房源照片作为页面中的主要视觉元素，其余装饰尽量简化。

### 1.3 视觉规范

| 设计元素 | 建议规范 |
|---|---|
| 主色 | `#176B68` 深蓝绿色 |
| 辅助色 | `#E8F3F1` 浅绿色 |
| 页面背景 | `#F7F9FA` |
| 卡片背景 | `#FFFFFF` |
| 主要文字 | `#202A2E` |
| 次要文字 | `#66757B` |
| 价格强调 | `#C65B42` |
| 错误提示 | `#BA3942` |
| 卡片圆角 | 12–16 dp |
| 按钮圆角 | 12 dp |
| 页面左右边距 | 16 dp |
| 组件间距 | 8、12、16、24 dp |
| 主要按钮高度 | 48–52 dp |

字体使用系统默认中文字体，避免额外增加字体包体积。

建议字号：

- 页面大标题：24 sp
- 模块标题：18–20 sp
- 正文：16 sp
- 辅助说明：14 sp
- 少量补充信息：12 sp

所有页面应适配系统字体缩放，不能通过固定高度导致大字体时内容被裁切。

## 二、APP整体导航布局

### 2.1 底部导航栏

APP采用底部五栏导航结构：

**首页 | 发布 | 意向 | 服务 | 我的**

五个模块分别承担独立的核心功能。

| 导航入口 | 对应功能 |
|---|---|
| 首页 | 房源浏览、搜索、筛选和详情 |
| 发布 | 创建房源、查看自己的发布记录 |
| 意向 | 固定回复、意向记录、联系授权 |
| 服务 | 第三方房评与过户代办服务信息 |
| 我的 | 用户资料、收藏、房源管理及设置 |

底部导航栏始终使用相同的排列顺序。

选中项使用主题色图标和文字，未选中项使用中性灰色。中间的“发布”入口可以略微突出，但不使用遮挡内容的大型悬浮按钮。

进入登录页、编辑表单或固定交流详情时，可以暂时隐藏底部导航栏，避免分散注意力。

### 2.2 整体导航层级

**一级页面：**

首页、发布、意向、服务、我的。

**二级页面：**

房源详情、筛选条件、发布表单、我的房源、意向详情、机构详情、个人资料。

**三级页面：**

联系授权确认、房源编辑、机构入驻申请、举报详情、设置子页面。

尽量将主要用户操作控制在三个导航层级以内。

## 三、首页UI布局

### 3.1 页面目标

让用户进入APP后立即看到房源，并能快速筛选和打开详情。

首页不需要大幅宣传图片，也不需要广告轮播。

### 3.2 页面结构

从上到下依次为：

**第一部分：顶部标题区域**

- 左侧：房市直通LOGO和文字。
- 右侧：当前城市或区域选择入口。
- 顶部采用白色背景。

**第二部分：搜索框**

- 宽度占据页面主要区域。
- 提示文字：“搜索小区、区域或房源”。
- 左侧搜索图标。
- 点击后进入搜索页面。
- 支持关键字输入及历史搜索。

**第三部分：快速筛选栏**

横向排列四个筛选入口：

- 地区
- 价格
- 面积
- 户型

点击后弹出筛选面板。

当前已选择的条件使用主题色标识，允许一键清除。

**第四部分：房源列表**

采用纵向滚动卡片列表。

每张卡片展示：

- 房源封面照片
- 小区名称
- 区域位置
- 房屋户型
- 建筑面积
- 出售总价
- 房源状态
- 最近确认在售时间

卡片左侧为图片，右侧为主要信息，便于用户快速浏览。

列表支持下拉刷新和滚动加载。

不建议第一版采用复杂的瀑布流布局，普通列表更适合房产信息对比。

**第五部分：底部导航栏**

保持五个主要功能入口。

### 3.3 首页交互

- 点击房源卡片进入详情。
- 点击收藏图标保存房源。
- 点击筛选项更新列表。
- 切换城市时重新加载对应地区房源。
- 滚动列表时顶部搜索和筛选区域可适当收起，增加内容展示空间。
- 列表为空时显示“暂无符合条件的房源”和“清除筛选”入口。

## 四、房源详情页UI布局

### 4.1 页面目标

集中展示用户判断房源价值所需的信息，并提供清晰的联系入口。

### 4.2 页面结构

**第一部分：图片展示区**

页面顶部使用横向图片轮播。

- 默认展示房源第一张照片。
- 点击图片进入全屏查看。
- 支持左右切换照片。
- 右下角展示当前图片序号，例如“2/6”。
- 图片加载失败时显示统一占位图。

**第二部分：房源核心信息区**

优先展示：

- 出售总价
- 小区名称
- 所在区域
- 建筑面积
- 户型
- 房屋楼层
- 装修情况

其中出售总价采用较醒目的字体，其他信息保持统一层次。

**第三部分：房源详细介绍**

展示房主填写的文字信息。

例如房屋朝向、装修状况、交通情况等。

内容支持展开和收起，避免长篇文字造成页面过长。

**第四部分：房源状态与说明**

显示：

- 当前状态：在售、暂停、已售出等。
- 最近确认在售日期。
- 发布者类型：房主、授权代理人等。
- 信息核验说明。

明确提示：

“房源信息由发布者提供，平台未进行专业产权核验，请在交易前自行核实。”

不使用“100%真实房源”等未经证实的宣传用语。

**第五部分：底部固定操作栏**

设置两个操作：

- 收藏
- 发起意向交流

“发起意向交流”为主要按钮。

如果房源已下架或已售出，则禁用意向交流按钮并展示原因。

## 五、房源发布页UI布局

### 5.1 页面目标

让普通用户无需专业房地产知识，也能完成一条房源信息的发布。

### 5.2 页面布局

采用纵向表单布局，将内容划分为四个区域。

**区域一：基础信息**

- 城市
- 所在区域
- 小区名称
- 建筑面积
- 户型
- 所在楼层与总楼层

尽量使用选择器、数字输入框和下拉选项，减少自由文本输入。

**区域二：价格与房屋情况**

- 出售总价
- 装修情况
- 房屋朝向
- 房屋描述

房屋描述使用多行文本框，显示剩余可输入字数。

**区域三：图片上传**

采用三列图片网格布局。

- 最多上传6张图片。
- 第一张作为封面。
- 支持删除和重新排序。
- 上传过程中显示进度。
- 上传失败时可以重试。

图片上传组件下方放置简短提示：

“请上传房屋实拍照片，避免包含身份证件、私人联系方式等敏感信息。”

**区域四：发布确认**

- 发布者身份选择。
- 信息真实性与发布权限声明。
- 房源状态及有效期说明。
- 提交审核按钮。

底部固定显示“保存草稿”和“提交审核”两个按钮。

### 5.3 表单交互

- 必填项使用清晰标记。
- 输入错误在对应字段下方提示。
- 离开未保存页面时提示是否保存草稿。
- 点击提交后显示加载状态，避免重复提交。
- 审核通过、驳回均有独立结果页面或状态提示。

不使用复杂的多级向导，第一版建议采用一页分区表单。

## 六、意向交流页UI布局

### 6.1 页面目标

通过固定问题和回复实现房屋买卖双方的初步联系，不引入自由聊天系统。

### 6.2 意向列表

页面顶部设置两个切换入口：

- 我发起的
- 我收到的

列表每项显示：

- 对应房源缩略图
- 小区名称
- 对方角色
- 当前交流进度
- 最近更新时间

例如状态显示：

“等待发布者确认房源是否在售”

“等待购房者确认联系意愿”

“双方已同意交换联系方式”

### 6.3 交流详情布局

采用类似聊天界面的视觉形式，但不允许用户自由输入内容。

页面顶部显示房源摘要。

下方为固定问答区域。

三个阶段依次为：

**阶段一：房源状态确认**

问题：“房屋目前是否仍在出售？”

可选回复：

- 仍在出售
- 暂停出售
- 已经售出

**阶段二：价格意愿确认**

问题：“房屋价格是否可以协商？”

可选回复：

- 可以协商
- 暂不议价

**阶段三：联系意愿确认**

问题：“是否愿意进一步交换联系方式？”

可选回复：

- 愿意
- 暂不愿意

已完成的问答以简洁消息卡片展示。

尚未轮到当前用户操作时，显示等待提示，不显示无效按钮。

### 6.4 联系方式交换页面

当双方均愿意继续联系后，进入联系授权环节。

页面展示：

- 对应房源摘要。
- 联系信息的公开范围说明。
- 当前用户拟共享的联系方式。
- 同意共享按钮。
- 拒绝共享按钮。

联系方式默认隐藏，只有双方明确授权后才展示。

授权完成后，可显示“复制联系方式”操作。

不增加在线语音、即时文字聊天或视频通话。

## 七、第三方服务页面UI布局

### 7.1 页面目标

为需要专业房产服务的用户提供机构信息查询渠道，但不在平台内完成服务交易。

### 7.2 页面结构

顶部标题为“第三方服务”。

下方设置服务分类：

- 房屋估价
- 产权咨询
- 过户代办
- 其他房产咨询

服务机构使用纵向列表卡片展示。

每张卡片包含：

- 机构或服务人员名称
- 所在地区
- 服务类型
- 服务介绍摘要
- 公开资质信息
- 查看详情入口

### 7.3 机构详情页面

依次展示：

1. 机构基本信息。
2. 服务范围。
3. 资质与主体信息。
4. 服务介绍。
5. 参考收费说明（如机构提供）。
6. 公开联系方式。
7. 第三方独立服务提示。

不设置在线购买、预约支付、服务派单等按钮。

### 7.4 第三方入驻入口

在“我的”页面中设置“申请成为第三方服务提供者”。

点击进入单独申请页面，填写基本资料并上传必要证明文件。

申请提交后显示审核状态。

第三方申请与普通房源发布流程相互独立。

## 九、注册与登录页面

登录页采用简洁的单列布局。

从上到下展示：

1. 房市直通LOGO。
2. 欢迎语。
3. 手机号输入框。
4. 验证码输入框。
5. 获取验证码按钮。
6. 登录或注册按钮。
7. 用户协议与隐私政策入口。

初期使用手机号验证码登录，不增加第三方社交账号登录。

游客可以浏览公开房源，但发布、收藏、发起意向交流等操作需要登录。

用户首次进行需要核验身份的操作时，再提示完成对应验证，避免在首次打开APP时要求填写所有个人资料。

## 十、管理后台UI布局

管理后台使用Flutter Web开发，优先适配桌面浏览器。

### 10.1 整体结构

采用左侧导航栏、顶部工具栏和右侧内容区域。

**左侧导航栏：**

- 工作台
- 房源审核
- 房源管理
- 用户管理
- 第三方机构
- 举报处理
- 系统设置
- 操作日志

**顶部工具栏：**

- 当前页面名称
- 管理员信息
- 退出登录

**主内容区域：**

根据当前模块展示数据表格、详情面板和操作按钮。

### 10.2 工作台页面

以简单统计卡片展示：

- 当前展示房源数
- 待审核房源数
- 已过期房源数
- 待处理举报数
- 待审核第三方申请数

统计数据以基础计数为主，第一版不需要复杂的数据可视化图表。

### 10.3 房源审核页

采用左侧房源列表、右侧审核详情的布局。

左侧展示待审核房源。

右侧展示：

- 房源图片
- 房屋信息
- 发布者信息
- 内容检查结果
- 审核通过按钮
- 驳回按钮
- 驳回原因输入框

涉及审核决定的操作需要二次确认并记录操作日志。

### 10.4 用户与举报管理

以数据表格为主体，支持按状态和时间筛选。

举报详情页面展示：

- 举报对象
- 举报原因
- 关联房源
- 必要的证据材料
- 处理状态
- 处理结果与备注

不得将其他用户敏感信息无差别展示给所有管理员，应根据管理权限限制可查看内容。

## 十一、统一组件库规划

Flutter项目中应提前制作可复用UI组件，避免不同页面重复设计。

| 组件名称 | 使用位置 |
|---|---|
| AppPrimaryButton | 提交、发布、确认等主要操作 |
| AppSecondaryButton | 取消、返回、辅助操作 |
| AppTextField | 搜索、表单输入 |
| AppDropdownField | 地区、户型、装修选择 |
| ListingCard | 首页、搜索、收藏 |
| ListingImageGallery | 房源详情 |
| ListingStatusLabel | 房源状态展示 |
| FilterChipGroup | 房源筛选 |
| InquiryOptionCard | 固定回复 |
| ContactConsentPanel | 联系授权 |
| ServiceProviderCard | 第三方服务列表 |
| EmptyStateView | 无房源、无收藏、无意向 |
| ErrorStateView | 加载或网络失败 |
| LoadingSkeleton | 房源列表及详情加载 |
| ConfirmDialog | 删除、下架、授权等重要操作 |

推荐使用Flutter Material组件作为基础，统一封装外观，而不是在每个页面独立设置颜色、圆角和按钮尺寸。

## 十二、页面适配与响应式布局

### 12.1 手机端

主要以360—430逻辑像素宽度设计。

采用单列纵向布局。

房源列表使用纵向卡片，详情页面以图片和文字分区为主。

屏幕较窄时筛选栏允许水平滚动。

### 12.2 平板端

利用较宽屏幕展示更多内容。

房源列表可以采用双列卡片。

搜索筛选面板可以改为侧边面板。

### 12.3 Web管理后台

大屏使用侧边栏与内容区。

中等宽度屏幕压缩侧边栏。

对于过窄的设备，提示使用更宽窗口或采用简化的管理布局。

移动端和管理后台共享颜色、间距、排版等设计规范，但不强制使用同样的导航结构。

## 十三、特殊状态与交互反馈设计

所有主要页面都需要覆盖正常状态之外的特殊情况。

### 13.1 加载状态

- 房源列表使用骨架屏。
- 图片加载使用占位图。
- 按钮提交过程中显示加载动画。
- 防止重复点击提交。

### 13.2 空状态

- 没有房源：显示空列表说明和清除筛选入口。
- 没有收藏：提示用户浏览房源并收藏。
- 没有意向：提示可以从房源详情发起交流。
- 没有机构：提示当前区域暂无第三方服务信息。

### 13.3 错误状态

- 网络断开：显示重试按钮。
- 图片上传失败：支持重新上传。
- 身份验证失败：显示具体错误原因。
- 房源被下架：停止联系入口。
- 对方拒绝交换联系方式：显示明确结束提示。

### 13.4 重要操作确认

删除房源、撤回联系授权、账户注销等操作均设置确认提示。

普通浏览和返回操作不应频繁弹出对话框。

## 十四、UI开发实施顺序

**阶段一：设计系统与导航**

完成主色、文字、间距、按钮、输入框、卡片等通用规范，以及底部五栏导航。

**阶段二：首页与房源页面**

完成首页、搜索筛选、详情和房源发布表单。

**阶段三：用户体系与个人中心**

完成登录注册、我的房源、收藏和账户设置。

**阶段四：意向交流**

完成固定问答、意向列表、双方联系授权。

**阶段五：第三方服务**

完成第三方机构列表、详情和入驻申请。

**阶段六：Flutter Web后台**

完成工作台、房源审核、举报处理和机构审核。

**阶段七：统一优化**

检查字体、按钮尺寸、页面间距、加载状态、错误反馈、深浅背景对比和不同屏幕适配。

## 十五、UI最终验收标准

1. 所有核心页面能够正常打开及返回。
2. 底部导航逻辑统一，不出现重复入口或导航混乱。
3. 房源信息层次清楚，用户能够快速看到价格、面积、户型和状态。
4. 用户能够通过清晰的表单完成房源发布。
5. 固定回复流程能够直观反映当前交流阶段。
6. 未经双方授权，页面不公开联系方式。
7. 不同尺寸手机上没有明显文字溢出、按钮遮挡或布局错位。
8. 页面具备加载、空数据、网络异常和操作失败提示。
9. 重要操作拥有明确的确认和反馈。
10. 管理后台能够高效完成房源、机构和举报审核。

---

## 十六、最终UI设计定位

房市直通的视觉设计不追求复杂的展示效果，而应以用户完成实际操作的效率为核心。

**首页突出房源，详情突出信息，发布突出效率，意向突出沟通，服务突出自主选择，个人中心突出管理。**

整个APP不添加与核心业务无关的页面，不使用复杂动画作为主要交互方式，不设置付费入口和交易流程。

通过Flutter统一设计组件、主题和布局规则，保证软件在开发初期具有较低的实现复杂度，同时具备后期持续迭代的能力。
